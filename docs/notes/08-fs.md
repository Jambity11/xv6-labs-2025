## 这个 Lab 真正在学什么

一句话：

> FS Lab 是在改 xv6 怎么把“文件”映射到磁盘块，以及怎么让一个路径名指向另一个路径名。

用户看到的是：

```text
write(fd, buf, n)
read(fd, buf, n)
open("a")
symlink("target", "link")
```

内核里面其实是：

```text
路径名 -> inode
inode -> 文件第几个逻辑块
逻辑块 -> 真实磁盘块号
磁盘块号 -> buffer cache / virtio disk
```

## 任务一：Large files

### 先用人话说

原始 xv6 的 inode 像一个小文件夹，里面只有 13 个格子用来记“文件内容放在哪些磁盘块”。

原来布局是：

```text
12 个格子直接指向数据块
1 个格子指向一级目录，一级目录里再放 256 个数据块地址
```

所以最大文件大概是：

```text
12 + 256 = 268 blocks
```

大文件任务要让一个文件能大很多，但不能把 inode 变大。办法是牺牲一个直接格子，换成二级目录：

```text
11 个直接块
1 个一级间接块
1 个二级间接块
```

二级间接块像目录套目录：

```text
二级间接块
  -> 256 个一级间接块
       -> 每个一级间接块再指向 256 个数据块
```

于是最大文件变成：

```text
11 + 256 + 256 * 256 = 65803 blocks
```

### 真实执行路径：写大文件

```text
用户程序 bigfile 写第 bn 个文件块
  -> write()
  -> sys_write()
  -> filewrite()
  -> writei()
  -> bmap(ip, bn)
  -> 如果 bn 在 direct 范围：
       用 ip->addrs[bn]
  -> 如果 bn 在 singly-indirect 范围：
       读 ip->addrs[NDIRECT] 指向的间接块
       在里面找数据块号
  -> 如果 bn 在 doubly-indirect 范围：
       读 ip->addrs[NDIRECT+1] 指向的二级间接块
       用 bn / NINDIRECT 找一级间接块
       用 bn % NINDIRECT 找数据块
  -> 必要时 balloc() 分配新磁盘块
```

### 真实执行路径：删除大文件

```text
unlink 或文件截断
  -> itrunc(ip)
  -> 释放 direct 数据块
  -> 释放 singly-indirect 指向的数据块，再释放 singly-indirect 块本身
  -> 遍历 doubly-indirect：
       对每个一级间接块，释放它指向的数据块
       释放一级间接块
  -> 最后释放 doubly-indirect 块本身
```

只改 `bmap()` 不改 `itrunc()`，文件能写大，但删除时会漏释放磁盘块。

### 怎么知道要改哪些文件

文件块寻址：

```text
kernel/fs.c       bmap(), itrunc()
```

磁盘 inode 格式：

```text
kernel/fs.h       struct dinode, NDIRECT, MAXFILE
```

内存 inode 副本：

```text
kernel/file.h     struct inode
```

文件系统镜像生成要跟磁盘格式一致：

```text
mkfs/mkfs.c       间接受 kernel/fs.h 影响
```

### 容易错的点

- 直接增加 `addrs[]` 长度，改变磁盘 inode 大小。
- 只改 `struct dinode`，忘记 `struct inode`。
- 二级间接索引的商和余数算错。
- 忘记在 `itrunc()` 里释放二级间接结构，导致磁盘块泄漏。
- 改了文件系统格式但复用旧 `fs.img`。

## 任务二：Symbolic links

### 先用人话说

符号链接就是一个“指路牌文件”。

它自己不是目标文件。它的内容是一段路径字符串：

```text
link 文件里面写着：请去打开 target
```

所以：

```text
symlink("target", "link")
```

意思是创建一个叫 `link` 的特殊文件，里面保存 `"target"`。以后用户 `open("link")` 时，内核默认会读出 `"target"`，再去打开 target。

硬链接不一样。硬链接是两个目录项直接指向同一个 inode；符号链接是一个独立 inode，内容只是路径字符串。

### 真实执行路径：创建 symlink

```text
用户程序 symlink("target", "link")
  -> 新系统调用
  -> sys_symlink()
  -> create("link", T_SYMLINK)
  -> 把 "target" 写入 link 这个 inode 的文件内容
```

注意：创建 symlink 时，`target` 可以不存在。因为 symlink 只是保存字符串，不是保存目标 inode。

### 真实执行路径：打开 symlink

```text
用户程序 open("link", 0)
  -> sys_open()
  -> namei("link") 找到 link 的 inode
  -> 发现 ip->type == T_SYMLINK
  -> 如果没有 O_NOFOLLOW：
       readi() 读出 link 文件里保存的 target 路径
       namei(target) 再找目标 inode
       如果目标还是 symlink，继续跟随
  -> 如果有 O_NOFOLLOW：
       不跟随，打开 link 本身
```

为了防止：

```text
a -> b
b -> a
```

这种循环，`open()` 要限制最大跟随次数。

### 怎么知道要改哪些文件

新增文件类型：

```text
kernel/stat.h      T_SYMLINK
```

新增打开标志：

```text
kernel/fcntl.h     O_NOFOLLOW
```

新增系统调用：

```text
kernel/syscall.h
kernel/syscall.c
kernel/sysfile.c   sys_symlink()
user/user.h
user/usys.pl
```

修改打开路径：

```text
kernel/sysfile.c   sys_open()
```

### 容易错的点

- 创建 symlink 时错误要求 target 必须存在。
- `open()` 跟随 symlink 时没有循环上限。
- 忘记 `O_NOFOLLOW`，测试无法打开 symlink 本身。
- `sys_symlink()` 放在 `create()` 定义之前，C 编译器可能报隐式声明/类型冲突。
- 误以为 symlink 和 hard link 一样直接指向目标 inode。

## 这个 Lab 最应该留下的理解

FS Lab 的两个任务都围绕 inode：

```text
Large files：
  改 inode 的 addrs[] 怎么解释，让一个文件能指向更多磁盘块。

Symbolic links：
  增加一种 inode 类型，它的内容是一段路径，open 时再按路径查找目标。
```
